## 1. Live location: hourly presence checks (server d4653c7, iOS 64b1bfb)

Between check-in and check-out, ALSO while inside the office, the phone records its position about once
an hour. Nothing before check-in or after check-out, ever (owner: tracking the commute was refused).
- Upload: the existing `POST /api/attendance/location-trail` accepts `event: "presence"` (classified and
  counted in outside episodes like `"point"`).
- A check is due 50 min after the last queued point, only while inside (or zone unknown). One precise
  window of ≤45 s; a fix ≤50 m ends it early; otherwise the best fix at timeout counts. No fix at all →
  retry after 15 min. A presence fix clearly outside becomes the EXIT point instead. Fixes coarser than
  1 km are never used for anything. Outside: unchanged (points every 15 min).
- iOS keeps the app alive cheaply between checks with a 3 km / 1 km-filter stream (no blue pill). On
  Android: the foreground service already runs for the shift — use a balanced/low-power request between
  checks and one high-accuracy request per check (FusedLocationProvider `getCurrentLocation` with
  PRIORITY_HIGH_ACCURACY + timeout 45 s). Update the persistent notification text honestly.
- Trail read `GET /api/attendance/records/{id}/trail` now also returns `presence: [{from, to, label,
  status, at}]` (status `inside|outside|unclear|pending|gap`, one per clock hour in the office's TZ,
  ≤17) and `record.locationTrackingState`. Draw a "Presence checks" row of hour chips (✓ ✗ ? – …) with
  "N of M hours at the office", and inside points as faint dots off the route line (see web
  `components/attendance/LocationTrail.tsx`, iOS `LocationTrailView.swift`).
- Server change: points now flip `locationTrackingState` to "on" only when it is empty (never over
  "denied").
- Disclosure / permission text must say: during work hours (check-in → check-out) NEXUS checks where
  you are about once an hour at the office and follows your route (~every 15 min) when you leave;
  nothing before check-in or after check-out.

## 2. Tracker resume bug (iOS 13e7784) — check the Android TrailMachine for the same class

iOS lost tracking after the app was killed and reopened outside: location was only started on a
*change*, so one missed start at launch lasted until the auto check-out. Fix = one idempotent
`reconcile()` deriving the location setup from saved state + permission, called at launch, on permission
change, on foreground/background, after every sync and every machine decision; on resume outside, the
first FRESH fix is uploaded at once (not after the 15-min throttle); fixes older than 2 min are ignored;
a fresh clear fix beats a stale geofence answer. Verify Android's service restart/boot/relaunch paths
behave the same.

## 3. Crew board

- **Score column** (web + iOS): `worked / working`. worked = days that are present (check-in) OR
  approved permit OR WFH. working = period calendar days − that person's EFFECTIVE day-off quota
  (default 4; some have 9; see §5 for extra days). Shown capped: `min(worked, working)/working`, and if
  worked > working a green `+N` beside it (a late >120 min day costs quota but is still worked).
  Examples: 31-day period, quota 4 → 27; quota 9 → 22; Farchan 25 worked, quota 9 → "22/22 +3".
  History rows now carry `user.dayOffQuota` (server c2ba2a1) — use it, fall back to 4.
- **Freeze panes + weekday labels** (iOS a9ca4f4, web): date row pinned on top with the weekday
  abbreviation above the day number (MON/TUE…, Indonesian SEN/SEL/RAB/KAM/JUM/SAB/MIN via the app's
  language), names pinned left, Score pinned right, today highlighted.
- **BoD "Change status"** (iOS 461cb65, web): tapping a cell (for BoD also id-less ABSENT/request rows
  and empty past days up to today; never future days) opens the day sheet with buttons Present ·
  Permit · Leave · Sick · Day off + "Clear penalty (restore XP & day-off)", each behind a confirm stating
  the consequence. API `POST /api/attendance/override { userId, date: "YYYY-MM-DD", action:
  PRESENT|LEAVE|SICK|DAY_OFF|PERMIT|CLEAR_PENALTY, note? }` → `{ ok, action, date, refunded,
  alreadyCovered?, closedAttendance?, multiDayRequestsLeft? }`; 409 `{error}` for a multi-day request
  conflict. Every action refunds that day's auto day-off cut + XP penalties. PERMIT keeps the day's
  check-in; LEAVE/SICK/DAY_OFF delete an open (no check-out) record. After success reload the board.
  Show the "Heads up" alert when `multiDayRequestsLeft > 0`.

## 5. Extra day off — LIVE (server e910294, 28 Sep 2026)

BoD grant X extra day-off days to selected people for ONE period (28→27); unused days expire. Effective
quota = member quota + non-revoked grants for that period — the server applies it everywhere (today,
deductions, requests cap, history `user.dayOffQuota`, exports). Android only needs to show the effective
quota it receives (the DO balance may read e.g. "1/7", tooltip/subtitle "4 + 3 extra"). A Control Room
grant screen exists on web and will be added to iOS; Android's Control Room is Phase 4 — do not build the
grant UI now. Push type `dayoff_bonus_granted` → channel `attendance_reminders`, link `/attendance`.
API (all need a session; errors `{error, code}`, Indonesian `error` shown as is):
- `GET /api/attendance/today` adds `dayOffAllowance {period, base, bonus, grants[{days, reason}]}`; `dayOffQuota` is already the raised figure — show "incl. N extra" when bonus > 0.
- `GET /api/attendance/day-off-bonus?periodKey=YYYY-MM` → `{periodKey, periodLabel, currentPeriodKey, canManage, grantablePeriods[3], mine:{base, bonus, quota}, grants[Grant]}` (staff see only their own grants).
- `POST /api/attendance/day-off-bonus` (BoD) `{userIds[], periodKey, days 1..31, reason 3..200}`; `DELETE /api/attendance/day-off-bonus/{id}` (BoD). Grant = `{id, userId, user?, periodKey, days, reason, createdAt, grantedBy?, revokedAt?, revokedBy?, active}`.
- History rows' `user.dayOffQuota`, deductions and dayoffs `quota` are all the period's effective allowance (dayoffs adds `baseQuota`, `bonusDays`, `bonusGrants`).
The grant screen lives in Control Room (web + iOS). Android: Phase 4 — don't build it now; just show the raised quota and route the `dayoff_bonus_granted` push.
